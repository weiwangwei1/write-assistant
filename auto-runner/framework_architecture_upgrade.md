# 写作框架架构改进方案 v1.0

> **文档目的**：分析当前写作框架为什么会导致「修 lint → 文学性退步」的恶性循环，
> 提出框架级（而非补丁级）的改进方案，供第三方审核。
>
> **审核要点**：本方案的改进是否正确识别了根因？提出的改进是否会产生新的问题？
> 是否有更好的替代方案？是否有遗漏的架构问题？
>
> **前置文档**：`auto-runner/rule_intents.md`（规则意图文档 v1.0）

---

## 一、问题陈述

### 1.1 现象

在《有龙则灵》Ch1-4 的生产过程中，发现了一个系统性的恶性循环：

```
写手写完 → style_lint 报错 → 写手修复 → 修复导致文学性退步 → 审核发现退步 → 再次修复 → 可能引入新问题
```

具体表现（7 种过度矫正模式）：

| # | lint 报错 | 写手的错误修法 | 后果 |
|---|----------|-------------|------|
| 1 | "像"字比喻超限 | 删掉最精准的比喻换成平叙 | 比喻有信息增量（温度/张力/状态），平叙没有 |
| 2 | "像"字比喻超限 | "像"改"如"骗计数器 | lint 看不到了，但比喻堆叠问题还在，且引入新的 AI 腔 |
| 3 | "了"密度高 | 删语法必需的"了" | "老灯累"（缺"了"）→ 语法残缺，读者以为打字漏了 |
| 4 | 碎段多 | 删"的""了"等连接词减字数 | "泛暗光"不如"泛了层暗光"自然 |
| 5 | 对话占比低 | 直接对话转叙述摘要 | "霍东来问许愿说没有"→ 失去现场感 |
| 6 | Tell 标记词 | 删所有心理描写 | 适度的内心独白是必要的，关键是展示而非宣告 |
| 7 | 确定性语气 | 所有描写都用"似乎" | 已确证的信息仍用"似乎"让角色显得迟钝 |

### 1.2 已实施的补丁（v2.2 框架升级）

针对上述现象，已识别 7 个根因（RC1-RC7）并实施了补丁：

| 根因 | 描述 | 补丁 | 位置 |
|------|------|------|------|
| RC1 | 反应式修复模式 | 5b 节「文学质量主动引导」+ 三条铁律 | chapter-writer SKILL.md |
| RC2 | 钝规则 vs 语义质量 | 比喻质量分级 + "了"模式检测 | style_lint.py v2.2.1 |
| RC3 | 缺失规则意图传递 | rule_intents.md 逐规则文档化 | auto-runner/rule_intents.md |
| RC4 | 对话规则无场景感知 | narrative_dialogue 检测 + certainty_state | style_lint.py + chapter-writer H3 |
| RC5 | 无合理覆写机制 | OVERRIDE 标记（每章≤3处） | style_lint.py Chapter 类 |
| RC6 | 反馈不回流 | feedback_collector.py 采集+回流管线 | auto-runner/feedback_collector.py |
| RC7 | 规则误报诱导矫正 | 正则精度改进 + 误报模式录入 | style_lint.py v2.2.1 |

### 1.3 补丁的局限性

**核心论点**：RC1-RC7 的 7 个补丁都是在现有架构内部打补丁，没有改变产生这些根因的架构本身。

补丁的效果类似于「给漏水的管子缠胶带」——每处漏水都缠了胶带，但管子的设计压力就没算对，新接头处还会漏。

证据：
- 补丁实施后，Ch1-4 仍然需要人工逐一修复过度矫正（`memory/feedback_rules.json` 记录了 6 个 active 模式）
- 每个补丁都在增加写手的认知负荷（rule_intents.md ~2000 tokens + feedback_rules.json ~500 tokens + 5b 节 ~800 tokens）
- 补丁之间存在张力：override 机制鼓励保留超阈值内容，但 lint 仍然阻断 → 写手不确定该用 override 还是该删

## 二、深层架构分析

### 2.1 三个架构级缺陷

RC1-RC7 不是独立的，它们是 **3 个架构级缺陷**的表现：

```
架构缺陷 A1：Lint 门禁制
  ├── RC1 反应式修复（门禁逼着写手修，修了又引新问题）
  ├── RC2 钝规则（门禁只能计数，不能判断质量）
  ├── RC5 无覆写（门禁不给例外，只能 hack）
  └── RC7 误报诱导（门禁报错了就得修，哪怕误报）

架构缺陷 A2：阈值化质量模型
  ├── RC2 钝规则（阈值假设"少=好"，但 3 个好比喻 > 8 个烂比喻）
  └── RC5 无覆写（阈值不给例外空间）

架构缺陷 A3：后置纠错模式
  ├── RC1 反应式修复（生成后纠错，不是生成时预防）
  └── RC3 缺失意图（纠错时不知道规则意图，乱砍一通）
```

### 2.2 架构缺陷 A1：Lint 门禁制

**现状**：style_lint.py 退出码 1 = 流水线阻断。L0（反 AI 红线）和 L1（作者身份规则）都是阻断性的。

**问题**：

1. **错误的激励结构**：当 lint 阻断时，写手的优化目标从"写好文"变成"过 lint"。这不是写手的错——是架构把激励设错了。

2. **判断问题被降级为计数问题**：写作质量是判断题（"这个比喻好不好"），不是计数题（"有几个比喻"）。门禁制把判断题变成了计数题。

3. **审核层退化为橡皮图章**：lint 过了 → 审核员默认"没问题"。但 lint 过了只代表计数合规，不代表质量过关。审核员本应是质量判断者，却变成了合规确认者。

4. **补丁的边际效益递减**：
   - override 机制：允许例外，但写手不确定该用还是该删
   - 比喻质量分级：区分好比喻和烂比喻，但仍在线阈值范式内
   - 规则意图文档：让写手理解"为什么"，但不改变"必须过"的压力
   - 每个补丁都在增加认知负荷，但核心矛盾（阻断=压力=过度矫正）没变

**核心矛盾**：门禁制假设"规则越严格=质量越高"。但实际上"规则越严格=过度矫正越多=质量越低"。

### 2.3 架构缺陷 A2：阈值化质量模型

**现状**：所有规则都是"≤X/章"或"X-Y%"的阈值。

**问题**：

1. **数量不等于质量**："≤8 个比喻"假设比喻数量与质量负相关。但 3 个精准比喻（"像一锅将开未开的水"——有温度有张力有状态）远好于 8 个陈词比喻（"像山一样""像火一样"）。阈值无法区分。

2. **场景不敏感**："对话占比 35-60%"假设所有场景的最优对话占比相同。但：
   - 探索/独处场景：对话自然偏少（可 <35%）
   - 交锋/谈判场景：对话自然偏多（可 >60%）
   - 一刀切的阈值逼着写手在探索场景硬塞对话，在交锋场景砍对话

3. **统计还原论**：风格包基于原作统计指纹设定阈值（如烟雨江南破折号 0/千字）。但统计告诉你"是什么"（她不用破折号），不告诉你"为什么"（她的长句本身就不需要破折号来制造停顿）。写手知道"≤0 破折号"但不知道"为什么不用"，就会在其他地方补偿性地用其他标点。

4. **比喻质量分级是改良，不是根治**：v2.2 的 classify_similes 区分优质/陈词比喻，优质占比≥70% 时超限降级为 minor。这是向语境感知迈出的一步，但它仍在阈值范式内——只是调了严重度，没改"用计数判断质量"的根本方法。

### 2.4 架构缺陷 A3：后置纠错模式

**现状**：生成文本 → 检查规则 → 修复违规 → 再检查 → 再修复……

**问题**：

1. **生成时才是最佳干预点**：避免 AI 痕迹的最佳时机是写的时候就注意，不是写完再修。rule_intents.md 和 feedback_rules.json 试图前移指导，但它们是"参考资料"，不是生成过程的结构性约束。写手读了，但不一定在写的时候想着。

2. **修复循环结构性不稳定**：每次修复都可能引入新问题。
   - 删比喻 → 可能碎段变多
   - 补对话 → 可能对话占比超标
   - 改"了" → 可能语法残缺
   - "修了不引新问题"是一条无法机器校验的软规则

3. **修复丢失原始意图**：写手写第一稿时有叙事意图（"这个比喻暗示能量积蓄"）。修 lint 时只看到"比喻超限"，不知道哪个比喻有意图、哪个是堆砌。于是全删，连有意图的也删了。

4. **前移指导的局限**：5b.4"主动合规"建议写手"写的时候就考虑规则意图"。但这是建议不是约束——写手仍然先写后修，因为 H2 要求"提交前 lint 全绿"，没要求"写作前先规划比喻位置"。

## 三、框架级改进方案

### 3.1 改进 F1：L1 规则从阻断降级为顾问

**解决的架构缺陷**：A1（门禁制）

**方案**：

将规则分级的阻断逻辑从"L0+L1 阻断"改为"仅 L0 阻断"：

| 级别 | 当前 | 改进后 |
|------|------|--------|
| L0 通用反AI红线 | 阻断（critical） | **不变**——阻断（critical） |
| L1 作者身份 | 阻断（critical） | **顾问**——报告但不阻断 |
| L2 签名手法 | 不阻断（minor） | 不变 |
| L3 偏好提示 | 不阻断（minor） | 不变 |

**具体实施**（style_lint.py）：

```python
# 当前
blocking = [i for i in all_issues if i.get("level") in ("L0", "L1") and i["severity"] == "critical"]

# 改进后
blocking = [i for i in all_issues if i.get("level") == "L0" and i["severity"] == "critical"]
advisory = [i for i in all_issues if i.get("level") == "L1" and i["severity"] == "critical"]
```

**配套约束**（防止 L1 降级后写手放飞）：

1. **审核员必须逐条回应 L1 advisory**：detail-reviewer 读取 lint 报告中的 L1 advisory 项，对每条给出"接受超阈值（附理由）"或"需修复"的判断。不能无视。
2. **quality-reviewer 检查 L1 advisory 是否被回应**：如果 detail-reviewer 没有回应所有 L1 advisory，quality-reviewer 标记为流程违规。
3. **连续 3 章 L1 advisory 同一条目超限**：触发 feedback_collector，自动将该规则升级回阻断状态。这是一个"信任但有验证"的机制——给写手自由，但如果反复犯同一问题，收紧。

**预期效果**：

| 过度矫正模式 | 改进后行为 |
|------------|----------|
| 删好比喻凑阈值 | 不需要删——lint 不阻断了，审核员判断比喻质量 |
| "像"改"如"骗计数器 | 不需要骗——计数器不拦你了 |
| 删语法必需的"了" | 不需要删——L2 本来就不阻断 |
| 对话转叙述摘要 | 不需要转——对话占比是 L1 advisory，审核员判断场景是否合理 |

**风险与缓解**：

| 风险 | 缓解 |
|------|------|
| 写手产出更多 AI 痕迹文本 | L0 仍阻断；L1 advisory 仍报告；连续 3 章超限自动收紧 |
| 审核员工作量增加 | advisory 项通常 ≤5 条/章，逐条判断 < 2 分钟 |
| 审核员判断标准不统一 | 配套 rule_intents.md 提供判断依据；quality-reviewer 抽查 |
| 写手滥用自由不修 advisory | 连续 3 章机制 + quality-reviewer 检查回应率 |

### 3.2 改进 F2：新增"风格规划"前置步骤

**解决的架构缺陷**：A3（后置纠错）

**方案**：

在 chapter-writer 写正文之前，新增一个"风格规划"步骤。写手在交接卡中填写 `style_plan` 字段，规划本章的风格执行策略：

```json
"style_plan": {
  "metaphor_plan": [
    {"position": "第2段", "target": "瓦当纹路觉醒", "metaphor": "像一条沉睡的蛇", "function": "外化能量积蓄状态"},
    {"position": "第5段", "target": "巷子氛围", "metaphor": "像一锅将开未开的水", "function": "暗示即将爆发"}
  ],
  "dialogue_plan": {
    "confrontation_scenes": ["霍东来质问许愿（第4段）"],
    "format": "直接对话（带引号+动作）",
    "reason": "面对面交锋，转述会失去现场感"
  },
  "rhythm_plan": "前3段短句密集（营造紧张感），第4段转长段（推理/氛围），结尾回短句（冲击）",
  "certainty_plan": {
    "许愿_公会": "first_encounter → 推测语气（倒像是）",
    "许愿_瓦当": "partial → 审慎语气（似乎）"
  }
}
```

**与 lint 的关系**：

- style_plan 在写作前填写，用于指导生成
- lint 仍然检查最终文本，但 style_plan 为审核员提供了"写手原本的意图"——审核员可以判断"这个比喻是有计划的还是随手堆的"
- 如果 lint 报"比喻超限"但 style_plan 显示每个比喻都有明确功能，审核员可以判定为"合理超限"

**预期效果**：

- 写手在生成时就考虑了比喻位置和功能，不再"先写一堆再删"
- 审核员有了意图上下文，判断更准确
- 修复 lint 时，写手可以参照 style_plan 知道哪个比喻该删（无计划的）哪个该留（有计划的）

**风险与缓解**：

| 风险 | 缓解 |
|------|------|
| 增加 token 预算（style_plan ~300 tokens） | 从 rule_intents.md 预算中削减（F1 降级后意图文档可精简） |
| 写手可能事后补填 style_plan | 交接卡提交时由总编检查 style_plan 是否在正文之前填写（时间戳） |
| style_plan 太详细限制创造力 | 只要求 metaphor_plan（比喻位置）和 certainty_plan（确定性），其余可选 |

### 3.3 改进 F3：规则生命周期管理

**解决的架构缺陷**：A1 + A2（规则膨胀 + 阈值固化）

**方案**：

为每条 lint 规则增加生命周期元数据，并通过 feedback_collector 自动追踪规则的健康度：

```json
// 在 RULE_LEVELS 或独立文件中定义
{
  "simile_total": {
    "level": "L1",
    "created_version": "v2.0",
    "last_reviewed": "2026-07-25",
    "overcorrection_count": 2,
    "false_positive_count": 0,
    "deprecation_criteria": "overcorrection_count > 5 或 false_positive_count > 3",
    "review_notes": "v2.2 增加质量分级后 overcorrection 下降，持续观察"
  },
  "narrative_dialogue": {
    "level": "L2",
    "created_version": "v2.2",
    "last_reviewed": "2026-07-25",
    "overcorrection_count": 0,
    "false_positive_count": 9,
    "deprecation_criteria": "false_positive_count > 5",
    "review_notes": "v2.2.1 修正则后误报清零，历史误报已录入 feedback_rules"
  }
}
```

**自动追踪机制**：

1. feedback_collector.py 扩展：从 detail_review 中提取过度矫正问题时，记录关联的 lint 规则名
2. 每次运行 feedback_collector 时，更新每条规则的 overcorrection_count 和 false_positive_count
3. 当某条规则触发 deprecation_criteria 时，自动在 feedback_rules.json 中标记为"需复审"
4. 总编定期（每卷末）复审标记为"需复审"的规则，决定保留/修改/废弃

**预期效果**：

- 防止规则膨胀：旧规则不再"只增不减"
- 量化规则健康度：不再凭感觉判断"这条规则好不好"
- 数据驱动决策：废弃一条规则有数据支撑，不是拍脑袋

### 3.4 改进 F4：修复差异审计器

**解决的架构缺陷**：A3（修复不稳定）

**方案**：

新增一个轻量级脚本 `fix_auditor.py`，在 lint 修复后、detail-reviewer 审核前运行，对比修复前后版本：

```bash
python fix_auditor.py output/chapter_001_pre_lint.txt output/chapter_001.txt --lint handoff/style_lint_ch1.json
```

**检测项**：

| 检测 | 方法 | 判定 |
|------|------|------|
| 语法残缺 | 对比修复前后：如果删了"了/着/的/地"，检查该句是否语法完整 | major |
| 比喻退步 | 对比修复前后：如果"像"字句被修改，检查是否变成了平叙 | major |
| 对话格式变化 | 对比修复前后：如果直接对话（带引号）变成了无引号叙述 | major |
| 同义词替换 | 对比修复前后：如果"像"→"如"/"似"/"仿佛"，"了"→"已"/"曾" | major（hack 绕过） |
| 新增 lint 问题 | 对修复后版本跑 lint，检查是否引入了新的 lint 问题 | minor-major |

**与 detail-reviewer 第8层的关系**：

detail-reviewer 的第8层（过度矫正检测）是**启发式**的——它只能从最终文本推断是否过度矫正，看不到修复前版本。fix_auditor 是**实证式**的——它直接对比修复前后版本，准确率更高。

```
chapter-writer 修复 lint
       ↓
fix_auditor 对比修复前后版本 ← 新增
       ↓
detail-reviewer 逐句审核（读取 fix_auditor 报告）
       ↓
quality-reviewer 宏观评分
```

**预期效果**：

- 过度矫正检测从"猜测"变成"实证"
- 审核员可以直接看到"修了什么、坏了什么"
- 修复质量可量化（引入新问题数 / 修复问题数 = 修复效率）

## 四、实施优先级

| 优先级 | 改进 | 理由 |
|--------|------|------|
| P0 | F1: L1 降级为顾问 | 最关键的架构变更，消除过度矫正的激励根源。改动最小（几行代码），影响最大 |
| P1 | F2: 风格规划前置 | 从被动修复转向主动规划。需要改交接卡格式和写手流程 |
| P1 | F4: 修复差异审计器 | 提升过度矫正检测的准确率。需要新脚本 + 保存修复前版本 |
| P2 | F3: 规则生命周期 | 长期治理规则膨胀。需要扩展 feedback_collector + 新增元数据文件 |

## 五、改进后的完整流水线

```
[风格规划 style_plan]     ← F2 新增：写手在写正文前规划比喻位置/对话格式/确定性状态
       ↓
[写正文]
       ↓
[style_lint 检查]
  ├── L0 反AI红线 → 阻断（不变）
  ├── L1 作者身份 → 顾问（F1 改进：报告不阻断）
  ├── L2 签名手法 → 顾问（不变）
  └── L3 偏好提示 → 顾问（不变）
       ↓
[fix_auditor 对比修复前后]  ← F4 新增：实证检测过度矫正
       ↓
[detail-reviewer 逐句审核]
  ├── 第1-7层（不变）
  └── 第8层 过度矫正检测（读取 fix_auditor 报告，更准确）
       ↓
[quality-reviewer 宏观评分]
  ├── 检查 L1 advisory 是否被逐条回应 ← F1 配套
  └── 检查 style_plan 是否被遵循 ← F2 配套
       ↓
[de-ai-processor / fanqie-adapter]
       ↓
[final-reviewer 终审]
       ↓
[memory-manager 入库]
       ↓
[feedback_collector 回流]  ← F3 扩展：更新规则健康度元数据
```

## 六、审核建议

请第三方审核员重点关注以下问题：

1. **F1 的风险是否被充分缓解？** L1 降级后，写手是否会产出更多 AI 痕迹文本？连续 3 章自动收紧的机制是否足够？

2. **F2 的 style_plan 是否会增加过多认知负荷？** 写手在写正文前还要填规划表，是否会影响创作流畅度？

3. **F3 的规则废弃标准是否合理？** overcorrection_count > 5 或 false_positive_count > 3 是否是合适的阈值？

4. **F4 的修复差异审计是否可行？** 需要在 lint 修复前保存一份 pre_lint 版本，这个流程约束是否太重？

5. **是否有遗漏的架构问题？** 除了 A1（门禁制）、A2（阈值模型）、A3（后置纠错）之外，是否还有其他架构级缺陷？

6. **是否有更好的替代方案？** 例如：完全废弃 lint 改为纯审核判断？或者引入 LLM 作为 lint 的语义判断层？

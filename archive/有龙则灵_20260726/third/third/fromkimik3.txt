## 一、内容/文本层面的修改建议

1. **给文风问题立量化红线（直接补进禁令清单）**：
   - "不是A——是B"每章 ≤2 处（设定级反转豁免，但需标注理由）；
   - ≤15字段落占比 ≤35%（现在的 65.8% 是对半砍都不够用）；
   - "像"字比喻每章 ≤8 个，且**禁止同一段落内多喻体堆叠**（一段一喻）；
   - 禁止"第N种热/第N种声音"式感觉编号（把现有的"一种"禁令扩成一类）；
2. **章首章尾规则从"类型轮换"升级为"意象去重"**：现在规则只禁止连续两章同类型，所以 A-B-A-B 也合规。改为：连续 4 章内章尾**收束意象**不得重复（光/鳞/醒/灯 算同族）；章首感官通道连续 3 章不得相同（现在 ch4 铁锈味、ch7 三种味道、ch12 灯油味全是嗅觉开场）。
3. **声口辨识度从"倡导"变"验收项"**：chapter-writer 里有"遮住名字能分辨谁是谁"，但没有任何环节真的执行这个测试。建议在 detail-reviewer 加一条硬操作：每章随机抽 5 句台词去名，写入交接卡让下一个 agent 盲测认领，认领失败即打回。
4. **桥段复用登记制**：把"你的棍子。掉了。"这类有意复现的桥段在 memory 里登记，复现时强制回答"增量是什么"（武器升级？对方有备？旁观者是新人？），无增量禁止复用。
5. **修时间线**：统一"上一次献祭"的定义（建议 60 年前庚午=灯熄献祭，20 年前=爷爷案，两者命名区分开，比如"庚午大祭"vs"许慎独案"），然后全文 grep 校验。
6. **发布前加"标签—内容一致性"检查**（归 fanqie-adapter）：位面元素出现在第几章、轻松基调占比、前 30 章与标签是否匹配——不匹配就二选一：改标签（"玄幻/民俗悬疑/轻松"比现在准确得多），或把位面元素前置到黄金三章埋线。

## 二、框架层面的修改建议

7. **最重要的架构改动：把可量化规则从提示词里拿出来，做成脚本 lint**。现在 73KB 的 SKILL.md 里混着两类规则——"庚午到庚午=60年要验算"这类**可机器校验**的，和"克制""氛围"这类**只能LLM判断**的。前者全部应该变成一个 Python 校验脚本（数句式、数碎段、数比喻、grep违禁词、对时间线），在写手提交交接卡**之前**跑，不过即打回。规则不靠 AI 的自觉执行——这次 8 处"一种"漏网已经证明了自觉不可靠。LLM 只评审 lint 覆盖不了的维度。
8. **废除"评分循环至 9.5"，改问题清单制**。现在 quality-reviewer 的分数全部挤在 9.3-9.6，没有区分度，"循环到 9.5"实际等于"循环到评审员愿意给 9.5"——LLM 自评的分数通胀是必然。改为：评审只输出 critical/major/minor 问题清单，清零即过，不打分。分数留给真正需要排序的场景（如大纲多方案比选）。
9. **给 SKILL.md 瘦身分层**。chapter-writer 24 节、73KB、几十条"硬约束"，已经超出 LLM 能稳定执行的信息量——规则越多，每条被执行的概率越低，而且互相打架（"超短句≥15%+段落≤4行"vs"每章至少1个200字长段"；"对话占比50-60%" vs 这本书实际的 35%）。建议：硬约束只保留 ≤10 条且全部可 lint；其余降级为"倾向/参考库"，按需调取。另外 README 还写着"7 个 Agent"，实际 17 个——文档也该同步。
10. **一致性系统补两个盲区**：①跨章事实表现在只核近章和数字，把**大纲远期设定的关键词**（如"上一次献祭""二十年前"）也纳入——写作时对设定圣经全文 grep 比对，就能拦住 ch5 那个矛盾；②longline-guardian 现在只看"伏笔库存"，加一项"设定表述与大纲原文逐字比对"。
11. **警惕"合并审核一次通过"**。日志里 ch2、ch3 是"detail+quality 合并审核一次通过"——这是用速度换掉了制衡，两个评审视角由一个 agent 一次性完成，等于自评自。建议至少保持写手与终审不同会话，或每 5 章抽样走一次完整独立双审。
12. **第三方评审常态化**。index-review（外部模型评审）是这套系统里最有价值的环节——ch4-10 的三大失控（爽点断顿/悬念过载/目标断头）全是它发现的，内部评审一个都没发现。建议从事后补救改为每 5 章固定跑一次，并规定内部评审与外部模型不同源。
13. **状态单一真相源**：进度、章节数、字数全部从 output 目录实时统计生成，禁止任何手写状态（"Ch1-10全部完成"这类头文件由脚本生成）。

## 三、速度/成本层面的修改建议

14. **交接卡瘦身，正文永不内嵌**。现在最大的浪费在巨型 JSON：parallel_review_ch2.json 61KB、skeptic_review 42KB、review_feedback 三轮累计 7 万+字节——每个 agent 都要重新读写全文。规定交接卡只传"问题清单+修改指令+文件路径"，正文一律引用文件，预估能砍掉 50% 以上的 token 消耗。
15. **评审轮次设上限**：quality 循环至 9.5 改为最多 2 轮，第 2 轮不过就升级人工或降级通过并登记，而不是继续刷轮次（ch1 曾 R1→R3 三轮，每轮都是全量重写+全量重审）。
16. **框架升级不追溯重写**。日志里 v1.6→v1.7→v1.8 三天内把黄金三章整体重写了三遍——这是最大的隐性时间成本。规则：框架迭代只适用于新章节，旧章的统一润色放到每卷结束后的复盘窗口做一次。
17. **审核环节并行化**：detail-reviewer / quality-reviewer / de-ai 目前串行，三者输入都是同一版草稿，完全可以并行跑再合并问题清单，每章能省约 1/3 的墙钟时间（日志显示目前每章 40-80 分钟，日更 2 章的目标按这个速度没有 buffer）。
18. **流水线化生产**：审第 N 章的同时写第 N+1 章（写手不等评审结果），把串行的"写→审→改→下一章"改成流水线，日更 2 章才可持续。

## 优先级排序

如果只挑五件事先做：**第 7 条**（lint 脚本化，一劳永逸解决文风漂移）、**第 8 条**（废评分制）、**第 2 条**（文风量化红线）、**第 10 条**（时间线比对）、**第 16 条**（停止追溯重写）。

最后说句公允的：这套框架的元能力——每次出问题后把教训写成规则（"数据依据：Ch1-9审核中5个critical错误…"）、爽点类型标注、悬念预算、第三方评审——方向都是对的，比绝大多数 AI 写作流水线认真。它的问题不是不严谨，而是**严谨全部用在了"流程和一致性"上，文风这块只写了倡导、没建检测**；而 LLM 恰好是"没被检测的东西一定漂移"。补上 lint 这一层，这套系统的产出会再上一个台阶。
